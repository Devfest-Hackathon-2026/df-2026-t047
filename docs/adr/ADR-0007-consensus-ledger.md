# ADR-0007: 合意台帳 — 会話の一貫性と時系列の合意を新しいアイデアに反映する

- Status: Accepted（2026-11-08 実装）
- Owner: TBD
- Updated: 2026-11-08
- 関連：仕様書v5 第6章（CAMP + Intent Fusion + Idea Lineage）、第8章（LLMに渡すコンテキストの階層化）、第24.1章の6（intentVersion）、ADR-0004・0005・0006

## Context

- これまで新しいアイデアの生成に渡していたのは「テーマ」と「既出の企画名」だけで、審査員の会話はまったく反映されていなかった。改良・回答も、その場の発言1件しか見ていなかった。
- 求めたいこと：
  - **一貫性**：みんなが合意したこと（例「コストは低め」）に、新しい案や改良が反しない
  - **時系列の合意**：誰が言い出し、誰が賛成し、いつ決まり、いつ覆ったかを追える
- 比較した方式：A 直近の発言をそのまま渡す／B LLM に要約を書き換えさせる／**C 合意台帳（採用）**。A は古い合意が消える、B は書き換えのたびにずれて誰がいつ言ったかが残らない。

## Decision

### 1. データの持ち方（イベントソーシング）

- **元の出来事**（追記のみ）：発言（`UtteranceRecord`：seq・審査員・文・宛先・意図）と行動（`DecisionRecord`：昇格・見送り・時間切れ退場・投票・優勝）。Firestore の確定イベントにも残る。
- **合意台帳**（`Ledger`、`apps/server/src/domain/consensus.ts`）：元の出来事から作る表。版番号 `version` を持つ。
  - 論点（Claim）：ラベル（C1…）・文・審査員ごとの最新の賛否・賛否の履歴（時系列）・確定（ピン留め）・置き換え先
  - 状態は**賛否から決定的に計算**する（LLM に決めさせない）
    - 合意：賛成が過半数（参加した審査員数の過半数。1人→1、2人→2、3人→2、4人→3）かつ賛成＞反対
    - 却下：反対が過半数、または賛成0で反対あり
    - 置き換え：新しい論点に置き換えられた
    - 確定（ピン留め）された論点は合意
  - 審査員の意見が変わったら最新の賛否だけを数え、履歴は残す（「最初は賛成、のちに反対」が追える）
  - 母数は「接続中」ではなく「参加した審査員」。切断で状態が揺れないようにするため

### 2. 自作プロトコル（CAMP）の拡張

| 追加 | 種別 | 内容 |
|---|---|---|
| `CONSENSUS_UPDATED { version, ops, statusChanges }` | Event | 台帳の差分。snapshot に `consensus { version, claims }` を同梱 |
| `PIN_CLAIM` / `UNPIN_CLAIM { label }` | Command | 人が「これで決まり」と確定・取り消し。LLM の抽出ミスを人が直せる |
| `SUBMIT_UTTERANCE.replyToClaim` | 項目 | 合意メモの論点への返答（👍👎ボタンもこれで送る） |
| `RevisionView.basedOnConsensus` | 項目 | どの版の合意をもとに作ったか（第24.1章の intentVersion に相当） |
| `RevisionView.inspiredBy { claimLabels, note }` | 項目 | どの論点を受けた案か（Idea Lineage）。フリップに 💡 で表示 |

### 3. LLM に渡すデータの整理（第8章の階層化）

```text
L0 固定：役割・ルール（systemInstruction）       … 毎回同じ
L1 審査の文脈：テーマ・合意台帳 vN の要約          … 版が変わるまで同じ文字列（renderContext）
   合意（守る）／提案中（参考）／却下（避ける）／選ばれた案／見送られた案
L2 直近の発言（6件）                               … 毎回変わる
L3 今回の処理（生成・改良・回答・台帳の差分）
```

- **台帳の更新は差分で**：前の台帳と、前回以降の発言・行動だけを渡し、`add_claim` / `set_stance` / `supersede` の**操作の列**を返させる。Zod で検証し、サーバーが順番どおりに当てはめる。LLM は文章を書き換えないので、ずれない・追える。
- 審査員は「審査員 A」、論点は C1、キャラは P1 のラベルで渡し、内部IDを扱わせない。知らない審査員・論点への操作は捨てる。
- 更新のタイミング：発言の2.5秒後（発言が続けばまとめる）、4件たまったらすぐ、昇格・見送り・投票の1.2秒後。実行は常に1件だけ。
- **反映先**：
  - 新しい案：合意・提案中の論点があれば、半分はそれを伸ばす案（`inspiredBy` 付き）、残りは新しい切り口の案（似た案ばかりにならないように）
  - 上段の改良：合意に必ず沿わせる。相互批評では合意に反する点を指摘する
  - 質問への回答：合意との関係に触れる
- 失敗したら固定データの簡易抽出（賛成・反対・要望の言葉）で代わりにする（`ResilientGateway`）。

### 4. キャッシュ

| 対象 | 方法 |
|---|---|
| L0+L1（プロンプトの前半） | 固定順・固定書式にして、Gemini の暗黙キャッシュが効く形にした。`cachedContentTokenCount` をログに出す |
| 作り置きの案 | 案ごとに `basedOnConsensus` を持たせ、合意が大きく動いたら（新しい論点・置き換え・状態の変化）古い作り置きを捨てて作り直す。すぐ補充できるよう、新しいものが無ければ1件だけ残す |
| 合意台帳・発言・行動 | アクターのメモリが正本、Firestore（セッション状態）が控え。再起動後も合意の流れが残る |

## Consequences

- 審査員の会話が、次の案・改良・回答に反映されるようになった。フリップの 💡 と合意メモで、会話がアイデアを動かしていることが目に見える（ピッチの見せ場）。
- 合意の判定が決定的なので、テストできる。LLM の役割は「発言から操作を提案する」ことに限定される。
- 呼び出しが増える：台帳の更新（発言のまとまりごとに1回、gemini-3.5-flash で約1.3秒）と、作り置きの作り直し。
- 文字列の長さが足りず、**暗黙キャッシュはまだ効いていない**（実測 `prompt≈850〜930 tokens, cached=0`）。会話が長くなり L1 が大きくなれば効く見込み。効かない場合は明示キャッシュ（セッション×台帳の版をキー）を検討する。最低トークン数は公式ドキュメントで要確認。

## Verification

- テスト（`apps/server/test/consensus.test.ts`、11件）：過半数の計算、提案 → 合意 → 意見が変わって提案中に戻る（履歴は残る）、ピン留め・置き換え、不正な操作を捨てる、保存と復元、発言をまとめて渡す・反映済みは渡さない、作り置きの作り直し、行動を材料に渡す、Gemini の操作の検証、L1 が同じ版で同じ文字列になること。
- ブラウザ＋本物の Gemini（2026-11-08）：
  1. 「実現コストは低めがいいな、学食の予算は少ないし」「留学生も楽しめる企画にしたい」→ C1「実現コストを低く抑える」・C2「留学生も楽しめるようにする」が合意に（台帳の更新 1.3秒）。古い作り置き2件を捨てて作り直し
  2. 新しい案に「💡 低コストで留学生と交流」「💡 留学生と気軽に交流」が付いて登場（残りは新しい切り口）
  3. 「やっぱりコストはそこまで気にしなくていいかも。話題性を優先しよう」→ C3「コストより話題性を優先する」が合意、C1 は「C3 に置き換え」。作り置きを再度作り直し
