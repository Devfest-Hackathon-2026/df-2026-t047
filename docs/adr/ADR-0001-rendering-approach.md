# ADR-0001: 描画方式 — DOM/CSS/SVG＋レイヤード素材を主体とする

- Status: Accepted（2026-11-07。比較・検証の項目は Verification に残る）
- Owner: TBD
- Updated: 2026-11-07
- 関連：仕様書v5 第22.2・22.7・27章、付録A／open-questions Q2

## Context

- 目標は参照画像の美術表現：濃紫のスタジオ、上下のリング状の舞台、ネオンLED、スポットライト、床の反射、もちもちした立体感のある非人間型マスコット、強く光るフリップ。
- フリップは**日本語の企画名と短い説明が読めること**が最優先。
- 主要な操作は**キャラ本体のドラッグ**。当たり判定とクリック／ドラッグの判別が重要。
- 低性能PC、1366×768、reduced-motion、キーボード操作にも配慮する。
- ハッカソンの工数でデモを安定させることを優先する。
- 「生成画像1枚を背景にして操作しているふり」は禁止（第27章）。

## Decision（提案）

**DOM/CSS + SVG + 事前に制作した透過素材（WebP/AVIF）+ Motion（Framer Motion）** を主体にする。

| 要素 | 実装方針 |
|---|---|
| スタジオ背景・照明 | 静的な背景レイヤー＋CSSのグラデーション／`mix-blend-mode`によるスポットライト。床の反射は反転した素材＋マスク |
| 上下のリング | SVGまたはCSS（`perspective` + `rotateX`）の楕円。グローは多層の `box-shadow` / `filter: drop-shadow` |
| キャラクター | 生成した透過WebPを1体あたり3ポーズ前後。呼吸・跳ね・持ち上げはCSS／Motionの transform で表現（下の「キャラの動きの作り方」を参照） |
| フリップ | DOMテキスト＋ネオン枠。文字はラスタライズしない |
| ドラッグ昇格・補充 | Motionの drag / layout アニメーション。光の軌跡はSVGパスまたはCanvasの部分利用 |
| 紙吹雪などの粒子表現 | 必要な箇所だけCanvasを部分的に使う |

**キャラの質感はエンジンではなく素材の出来で決まる**、という判断が前提にある。

### キャラの動きの作り方（Q2暫定回答、2026-11-07）

**まず試す方針**：画像生成AIで作った静止画を1体あたり数パターン（待機／発表／掴まれ中など）用意し、操作に反応する動きはコードで付ける。**動画AIの利用は選択肢として残す**。

判断の根拠：22.7の優先度上位の動き（ドラッグ昇格、補充の登場、上段の進化）は、カーソルへの追従、途中での中断、サーバー拒否時の戻り、生成完了のタイミングに合わせた切り替えが必要で、決まった長さの動画では作れない。

| 動き | 方式（暫定） |
|---|---|
| 待機中の呼吸・跳ね、ホバー時の反応 | 静止画＋CSS／Motion（上下の揺れ・軽いつぶれ伸び・影の伸び縮み） |
| ドラッグで持ち上げる、光の軌跡、拒否時に戻る | Motion（コード） |
| 補充の登場 | コード（スポットライト＋拡大して着地） |
| 表情の差分 | 生成した静止画の切り替え |
| 優勝演出・開幕演出 | **動画AIの候補**（一発もので、操作は不要） |
| 待機ループ | **動画AIの候補**（透過・同時再生の検証に通れば） |
| 余力があれば（P1） | 目立つ数体だけ、頭・耳・体のパーツに分けて軽くリグを付ける（Rive等） |

動画AIを使う場合の課題（要検証）：
- 生成動画はふつう背景が透けない。クロマキー等で抜く必要がある。透過動画の形式はブラウザによって異なる（ChromeはVP9 alpha WebM、SafariはHEVC alphaが候補）。
- 16体×状態の数だけクリップが必要。キャラの見た目の統一と工数。
- 画面上の5〜8体を同時に再生したときのデコード負荷。
- 状態を切り替えるときの継ぎ目。

素材生成に使うツール（ChatGPTの画像生成、Gemini／Imagen、Veo等）は、出力物の利用規約を確認したうえで決める。

### 比較試作（実装の許可後に実施）

試作画面の1体（例：SPROUT）で次の3つを並べ、質感・動きの自然さ・FPS・制作時間を比べる。

- (a) 静止画1枚＋CSS／Motionで揺らす
- (b) 頭と体の2パーツに分けて揺らす
- (c) 動画AIで作った待機ループを透過して表示する

## Alternatives

| 案 | 利点 | 欠点 |
|---|---|---|
| React Three Fiber主体 | 本物の奥行き・ライティング・カメラ演出 | 3Dキャラ素材の制作コストが大きい。日本語テキストの可読性、当たり判定、低性能PCのFPSがリスク |
| PixiJS主体 | 2D表現で高いFPS、粒子表現に強い | テキストやアクセシビリティをDOMと二重管理することになる。Reactとの統合に手間がかかる |
| ハイブリッド（DOM主体＋R3Fは優勝演出だけ） | 見せ場だけ3D | バンドルサイズとコンテキストの切替コスト。P2で検討 |

## Consequences

- 利点：フリップの可読性、Reactコンポーネントとの親和性、ドラッグ実装の容易さ、アクセシビリティ、チームの学習コスト。
- 欠点：本物の3Dカメラワークはできない。奥行きは「2.5Dの見せ方」で作る必要がある。
- **最大のリスクはキャラ素材の制作**。補充のたびに別デザインが必要なので、12〜16体程度のプールが必要になる見込み（Q2）。

## Verification（スパイク案）

1. 下段5体＋上段3体＋フリップ8枚＋グロー＋スポットライトを1画面に配置し、1366×768の低性能ノートPCで60fps近くを保てるか測る（Performanceパネル）。
2. 参照画像とスクリーンショットを並べ、質感・リングの奥行き・光の強弱を比較する。
3. ドラッグ中の持ち上げと光の軌跡がカクつかないか確認する。
4. `prefers-reduced-motion` のときの代替表現を確認する。
