## 1. 発表のアプローチ

### まず確かめること

- 持ち時間、質疑の時間
- 審査の観点（DevFest の審査基準）
- 会場でライブのデモができるか（ネット回線・音の出し方・マイク）

### 構成の案（持ち時間が分かったら配分する）

1. **つかみ**：「まだ、人間がアイデア出してるの？」。会議でアイデアが出ない・声の大きい人の案に決まる、という困りごと
2. **答え**：AI がアイデアを出し、人間は「おもろいかも」を選ぶだけ。審査員として判断に集中する
3. **デモ**：テーマを入れる → キャラが案を出す → ボタンで選ぶ → 決勝で磨く → 優勝 → 企画書がすぐ出る
4. **しくみ**：好みを読む（8軸）、会話から論点と合意を記録する、決勝で相互批評して改良する
5. **効果の数字**：3章の数字（実測・試算・予備実験を分けて）
6. **技術**：複数人がリアルタイムで同時に操作しても壊れない。そのための通信の約束（CAMP）を OSS として公開した
7. **これから**：会議ツールへの組み込み、など

### デモのやり方

- ライブで見せるのが一番強いが、回線・声・AI の待ち時間で止まることがある
- **録画の予備は必ず用意する**。ライブで止まったらすぐ録画に切り替える
- 台本を作り、テーマと話すことを決めておく（同じ流れを何度か通しで練習する）

## 2. 強みの候補（2〜3個に絞る）

| 候補 | 言い方の例 | 見せ方 |
|---|---|---|
| 役割の逆転 | アイデアを出すのは AI、判断するのは人間 | つかみとデモ |
| 好みを読んで出す案が変わる | 選んだ・話したことから一人一人の好みを読み、次の案に反映する | 8軸グラフ（D1 #12）、好みを読んだ後の案が選ばれる率 |
| 会話が企画に残る | 話したことが論点・合意として記録され、企画書の根拠になる | 合意メモ、企画書 PDF |
| 判断で案が進化する | 人間の指示と相互批評で案が改良され、版をたどれる | 改良の履歴（B4 #8） |
| 会議の時間が短くなる | 15分で、根拠つきの企画書まで出る | 3章の試算 |
| 複数人で同時に触っても壊れない／OSS | 通信の約束を標準化して公開した | CAMP の実測（3-5） |
| Google の技術を使い切っている | Gemini（構造化出力・Live の文字起こし・埋め込み）、Cloud Run、Firestore | 構成図 |

DevFest（Google のイベント）なので、Gemini と Google Cloud の使い方は説明に入れたい。

## 3. 効果を示すデータ

ユーザーへのヒアリングが難しくても取れるものから順に並べる。架空の数字は出さない。値が少ないときは「n＝○」「予備」と必ず書く。

### 3-1. アプリのログから自動で取れる数字（実測）

1回のオーディションごとに出せる。遊ぶたびに数が増える。

| 指標 | 意味 | 今 |
|---|---|---|
| 出た案の数・1分あたりの案の数 | アイデアがどれだけ出たか | 記録はある。集計が無い |
| 開始から優勝までの時間 | 1案に決まるまでの時間 | 記録はある。集計が無い |
| 優勝から企画書が出るまでの時間 | 企画書づくりにかかる時間 | ログに出る（前もって作るので 0秒にできた） |
| 発言・操作の偏り | 一部の人だけが話していないか（参加の均等さ） | 記録はある。集計が無い |
| 好みを読んだ後の案が選ばれる率 | 好みの読みが効いているか | `computeMetrics` にある（前回は件数が少なく結論なし） |
| 人間の意見が案に反映された率 | 話したことが案を変えたか | 前の計画のフェーズ2（因果の記録）が未実装 |
| キャラの返事の速さ | 待たされないか | ログに出る |

### 3-2. 会議に入れたときのメリットの試算（推計）

実測ではないので、**前提と出典をすべて書く**。

- 例：ふつうのアイデア出しの会議（○人×○分）＋企画書づくり（○時間）と、IDEA AUDITION（15分で企画書まで）の比較
- 会議の時間・人数・時給などの前提は、公的な調査や公開データから取り、出典を書く
- 「1回あたり○人時」「月○回なら○時間」のように、前提を変えたらどう変わるかも示す
- 3-1 の実測値（決まるまでの時間など）を、試算の材料に使う

### 3-3. 終わったあとのアンケート（アプリの中）

ヒアリングの代わりに、遊んだ人全員から短く集める。

- 優勝画面のあとに、7段階で3問ほど：納得できたか、参加できた感じがあるか、また使いたいか。自由記述1問
- Firestore に保存して、発表の前に集計する

### 3-4. 小さな比較実験（予備）

前の計画のフェーズ5。「ふつうのチャット AI を使って15分で1案に決める」と「IDEA AUDITION で15分」を比べる。人数が集まらなければ、やり方と予備結果までにする。

### 3-5. 技術の実測（CAMP）

前の計画のフェーズ4。同時操作での食い違いが0、再接続で操作がちょうど1回だけ反映、などを再現できるスクリプトで測る。「壊れない」を数字で言うためのもの。

## 5. 考え（優先度の提案）

- 締切は明日なので、アプリの13件とこちらを全部はできない。**発表に直結するものを先に**する
- 先にやるもの：P1（すぐ終わり、残りの全部の前提になる）→ P2 → M1 と M3（遊ぶたびにデータが貯まるので、早く入れるほど数が増える）→ P3・P4
- M2（試算）は半日かからない。M1 の実測値が少しでも出てから入れる
- M4（比較実験）は人を集める必要がある。集まらなければ、やり方だけ書いて「今後」に回す
- M5 は CAMP の公開を強みとして話すなら必要。話さないなら後回しでよい
- 遊ぶときは毎回本番で遊ぶ（ログとアンケートが本番に貯まる）。本番のデータを集計するときは、読み取りの権限をどうするか決めておく
