# ADR-0005: Gemini非同期オーケストレーション

- Status: Accepted（2026-11-07。比較・検証の項目は Verification に残る）
- Owner: TBD
- Updated: 2026-11-07
- 関連：仕様書v5 第5・8・22.4・22.6・25.3章／open-questions Q3, Q5

## Context

- 下段は常に5体が新しい案を発表し、上段は最大3体が並行して改良を進める。**上段の進化中も下段の生成を止めない**。
- 補充はドラッグ直後に起きる。Geminiの応答を待ってから補充すると、空席が目立つ。
- 上段では「元案／残す強み／改善ポイント／改良版」と相互批評を**見える形**で出す必要がある。
- 遅れて返ってきた応答が新しい指示を上書きしてはならない。
- 外部APIなしでも通しデモができる必要がある（付録A）。

## Decision（提案）

### 1. ポートと偽ゲートウェイ

- `IdeaGenerationPort`（application層）を定義し、`GeminiGateway` と `FixtureGateway`（固定データ）を実装する。
- デモ・開発・テストでは `FixtureGateway` に切り替えられる。本番デモで通信が落ちたときの代わりにもなる。
- APIキーはサーバー側だけに置き、クライアントに渡さない。

### 2. 優先度つきジョブキュー

| 優先度 | ジョブ | 備考 |
|---|---|---|
| 1 | 上段の改良（REFINE） | 見せ場。昇格直後に投入する |
| 2 | 補充用の先読み（PREFETCH） | ストックが閾値を下回ったら投入する |
| 3 | 下段の次の案（NEXT_IDEA） | 発表済みの案の入れ替え用 |

- 同時実行数はレート制限と実測レイテンシーで調整する（値は未定）。

### 3. 先読みストック

- 未発表の候補（キャラ割当て済み、またはキャラ未割当てのアイデア）を**常に2〜3件**ストックする。
- 昇格が確定したらストックから即座に補充し、裏で先読みジョブを投入する。
- キャラは補充時に素材プールから選ぶ。直前に昇格したキャラ、および上段・下段に表示中のキャラとは別デザインを選ぶ（AC-03, AC-05）。

### 4. 上段の改良パイプライン

- **1回の構造化出力で、分析→改善点→改良版をまとめて受け取り**、UIで段階的に見せる（批評の吹き出し→改善点のハイライト→フリップ公開）。
- 出力スキーマ（案）：`keepStrengths[]`, `improvementPoints[]`, `critiques[{fromFinalistId, text}]`, `revised{title, summary}`, `inheritedFrom[{ideaId, reason}]`。
- サーバーでスキーマ検証する（Zod等）。不正なら1回再試行し、それでも失敗したら安全なデフォルト表示にする。
- 改良は新しいRevisionとして保存し、元のRevisionは不変（AC-23）。

### 5. 古い応答の破棄

- ジョブに `revisionBaseVersion` と `intentVersion` を付ける。結果が返った時点で現在の版と一致しなければ、結果を破棄するか再投入する。

### 6. 改良トリガーと相互批評（Q3回答済み、2026-11-07）

**トリガー**（これ以外では改良しない。定期的な自動更新はしない）：

| トリガー | 対象 | 内容 |
|---|---|---|
| 昇格直後 | 昇格したキャラ | 分析→改善点→改良版を1回 |
| 審査員の明示的な改善指示 | 指示を受けたキャラ | 指示を反映した改良版を1回 |
| 新しいキャラが上段に加入 | 上段の全員 | 相互批評（2〜3ラウンド）→各自の改良版 |

- **質問**は回答を生成するだけで、Revisionは作らない（AC-14）。

**相互批評：1回のトリガーにつき2〜3ラウンドの往復**

- ラウンドの構成（案）：R1 指摘 →R2 反論・再提案 →R3 歩み寄り（任意）→ 各自の改良版。
- 呼び出し方は2案を比較する（**要検証**）。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A：一括生成（第一候補）** | 1回の構造化出力で、全ラウンドの台詞と改良版をまとめて生成する。UIで1ラウンドずつ順に見せる | 待ち時間は1回分。コストを予測しやすい。途中で失敗しない | 全体を受け取るまで最初の吹き出しが出ない。ラウンドの途中で人の指示を反映できない |
| B：ラウンドごとに呼ぶ | 1ラウンドごとに生成する。前のラウンドの台詞を次の入力にする | 最初の吹き出しが早く出る。ラウンド間に人の指示を差し込める | 待ち時間とコストがラウンド数倍に増える。途中で失敗した後の扱いが要る |

- 出力スキーマは §4 の `critiques[]` を拡張する：`critiques[{round, fromFinalistId, toFinalistId, replyToId?, text}]`。
- 表示の制約（案）：吹き出しは1つ40字前後、同時に表示するのは最大2つ、読める速さで順に出す。発話はさせず視覚表示を基本とする（22.4の音声フォーカス）。
- **途中で割り込まれたとき**：批評ラウンドの表示中に、審査員の明示指示または新しい加入が起きたら、表示中のラウンドは最後まで見せたうえで、未公開の改良版を `revisionBaseVersion` で古いものと判定して破棄し、新しいトリガーで生成し直す。
- 1つのトリガーで動く批評は1件だけにする（同じ上段で批評ジョブを並行させない）。

### 7. 音声（Q5回答済み、2026-11-07）：P0からGemini Live

**決まったこと**：審査員の音声入力は、P0からGemini Live APIで扱う。

**構成の暫定案**（すべて要検証）：

- 各PCのブラウザが、自分のマイク音声をGemini Liveへ送る。接続方式は2案を比べる。
  - (1) クライアントから直接つなぐ。サーバーが短命のトークンを発行し、APIキーはブラウザに渡さない。
  - (2) Cloud Runが中継する。
  - 公式ドキュメントで短命トークンの対応状況を確認してから決める。
- 認識結果（文字起こし・意図）は、CAMP のCommand `SUBMIT_UTTERANCE{text, source: "live" | "text"}` としてサーバーに送る。音声そのものは操作用のWebSocketに流さない（9.2）。
- サーバーは発言を `JUDGE_UTTERANCE_RECEIVED` として記録し、意図の抽出（質問か、改善指示か）を行う。質問と改善指示の区別（AC-14）はサーバー側で確定する。
- マイクは各自がON/OFFできる。AIの発表中も人間は話せる（25.3）。

**デモを止めないための代わりの手段（必須）**：

- テキスト入力欄を常に使える状態にしておく（`source: "text"`）。Liveの接続が失敗・切断したら、自動でテキスト入力に切り替えて画面に表示する。
- `FixtureGateway` のモードでも、テキスト入力で通しデモができる（AC-33）。

**リスク（要検証）**：

- 4台のPCから同時にLiveのセッションを張れるか、レート制限・同時接続数・料金。
- 日本語の認識精度と遅延。
- 同じ部屋の4台が互いの声やAIの発表音声を拾う（ハウリング・誤認識）。デモではヘッドセットを使うか、AIの発表は字幕を基本にする。
- セッションの最大継続時間と、再接続の手順。

**最初に試すこと（初日）**：ブラウザ1台からLiveにつなぎ、日本語の発言が数秒以内に文字になるか。続けて2台を同時につなぐ。

## Alternatives

| 案 | 利点 | 欠点 |
|---|---|---|
| 段階ごとに別々に呼ぶ（分析→批評→改良） | 各段階をストリーミングで見せられる | 待ち時間が合計で長くなり、呼び出し回数とコストが増える |
| 生成を同期で待つ | 実装が単純 | 操作をブロックし、AC-24に違反する |
| クライアントから直接Geminiを呼ぶ | サーバー不要 | APIキーの露出、排他・整合性を保証できない |

## Consequences

- まとめて呼ぶ方式は、1回の失敗で全段階をやり直すことになる。
- 先読みストックは、テーマ変更時に破棄する必要がある（stale candidate）。
- Idea Lineage（継承元と理由）は `inheritedFrom` で記録し、Firestoreに保存する。

## Verification

1. REFINE / PREFETCH の生成時間をp50/p95で測る（モデル名は検証時に決める）。
2. 上段3体が改良中でも、下段の補充が1秒以内に見えるか（ストックから補充されるか）。
3. 構造化出力の不正率と、再試行後の成功率。
3-2. 相互批評の案A（一括）と案B（ラウンドごと）で、最初の吹き出しが出るまでの時間と、改良版が公開されるまでの時間を比べる。2〜3ラウンドの往復が、見ていて冗長にならないかも確認する。
4. `FixtureGateway` だけで、テーマ設定→発表→選抜→進化→優勝を完走できる。

## 実装メモ（2026-11-07）

- **Vertex AI 経由**で呼ぶ（`@google/genai` の `vertexai: true`、`location: global`）。Cloud Run ではサービスアカウントで認証し、**APIキーは持たない**。GCP クレジット（請求先 VICTORY）がそのまま適用される。
- ローカル開発では `LOCAL_GCLOUD_CONFIG=victory` を設定すると、サーバーが `gcloud auth print-access-token` でトークンを取得・更新する。マシン全体の ADC は上書きしない。
- モデル（環境変数で変更可）：
  - 案の生成・回答：`gemini-3.5-flash`（thinking MINIMAL）
  - 上段の改良・相互批評：`gemini-3.8-flash`（thinking LOW。MINIMAL は非対応）
  - `gemini-3.5-flash-lite` は速いが文字数の指定を守らないことがあったため不採用
- 実装：`apps/server/src/infrastructure/gemini/`。出力は JSON Schema（Zod から生成）で受け取り、Zod で検証。不正なら1回やり直し、それでも駄目なら `ResilientGateway` が固定データで応答する。
- 相互批評の「誰が誰に言うか」はモデルに任せず、サーバーが決めた順番を使う。モデルには内部IDを渡さず P1, P2… のラベルで扱わせる。

### 実測（ローカル → Vertex AI global、各1〜数回。統計的な値ではない）

| 処理 | モデル | 時間 |
|---|---|---|
| 案の生成（3〜8件） | gemini-3.5-flash | 1.2〜4.2秒 |
| 上段の改良（1体） | gemini-3.8-flash | 2.6秒 |
| 上段の改良（2体＋批評2ラウンド） | gemini-3.8-flash | 4.1〜9.3秒 |
| 上段の改良（審査員の指示） | gemini-3.8-flash | 6.9秒 |
| 質問への回答 | gemini-3.5-flash | 1.1秒 |

改良は最長で10秒近くかかる。先読みストックがあるので下段の補充は待たないが、上段の「分析・ブラッシュアップ中」の時間が長く見える場合は、ストリーミングで批評だけ先に出す案（案B）を検討する。

## 実装メモ：Gemini Live の音声入力（2026-11-07）

- **接続方式：サーバー中継（案2）を採用**。ブラウザ → `/voice`（操作用の `/camp` とは別の WebSocket）→ Cloud Run → Gemini Live。認証はサーバーだけが持つので、ブラウザにトークンを渡さない。短命トークン方式（案1）は Gemini Developer API 向けで、Vertex AI では使わない。
- **モデル**：`gemini-3.5-transcribe-live`（location `global`、出力は TEXT のみ）。文字起こし専用で音声の返答を作らないため費用が小さい。途中経過（interim）と確定結果が返る。
  - 比較：`gemini-live-2.5-flash-native-audio` は `us-central1` でのみ接続でき、音声の返答も生成する。文字起こしが「{} る な もう 少し…」のように崩れたため不採用。
- 音声形式：16kHz・モノラル・16bit PCM。ブラウザの AudioWorklet で変換して約100msごとに送る。
- **発言のまとめ方**：確定結果が細かく区切られ、区切りの先頭が欠けることがある（例：途中経過「ルナ留学」→ 確定「留学生も楽しめる」）。無音が1.2秒続くまで連結し、直前の途中経過と重なる位置から欠けた先頭を補う（`UtteranceAssembler`）。モデルが先頭の聞き間違いを直した場合も古い先頭が残るが、宛先の名前を落とさないことを優先した。
- **宛先**：発言に含まれるキャラ名（英字名または読み）→ 詳細を開いているキャラ、の順に決める。上段キャラへの質問以外の発言は改善の指示として改良を依頼し、それ以外は回答だけを返す（AC-14）。質問か指示かの判定は引き続き正規表現の仮実装。
- テキストでの発言欄を常に表示する。マイクを使えない・接続できない場合はトーストで知らせ、テキスト入力に切り替える。
- マイクを OFF にすると Live の接続も閉じる（音声を流している間だけ費用がかかる）。

### 実測（macOS の合成音声 Kyoko をスクリプトで送信。実際の人の声・マイクでは未検証）

| 発言 | 文字起こし | 処理 |
|---|---|---|
| 「ルナ、もう少し実現コストを下げられないかな？」 | ルナ、もう少し実現コストを下げられないか | 下段の LUNA への質問 → 回答 |
| 「ルナ、留学生も楽しめるようにして」 | るな留学生も楽しめるようにして。 | 上段の LUNA への指示 → 改良版 v3（「留学生も楽しめるよう多言語化と世界の料理を導入」） |

- Live の接続確立：0.4〜0.9秒。確定までの遅れ：話し終わりから約1.2秒（まとめのための待ち時間を含む）。
- 補う処理を入れる前は、2つ目の発言が「留学生も楽しめる」「して」に分かれ、宛先が付かなかった。

## 実装メモ：AI のモード切り替え（2026-11-08）

- セッションごとに AI のモード（`gemini` / `fixture`）を持つ。開始画面で選び（`START_AUDITION.aiMode`）、途中でもホストが切り替えられる（`SET_AI_MODE`、`AI_MODE_CHANGED`）。snapshot の `ai { mode, available }` で全員に共有。
- 目的：AI の精度改善で同じ流れを Gemini と固定データで比べる／UI の作業やデモの練習でクレジットを使わない。
- サーバーが `AI_GATEWAY=gemini` のときだけ Gemini を選べる（既定は Gemini）。固定データは常に選べる。切り替えたら、前のモードで作った作り置きを1件だけ残して作り直す。
- チーム向けの使い方とクレジットの節約ルールは `docs/05-platform/gemini-credits.md`。
