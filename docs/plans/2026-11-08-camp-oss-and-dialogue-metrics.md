# 実装計画：CAMP の OSS 公開と、人間×AIの対話の実測

- Date: 2026-11-08（締切 2026-11-10）
- Status: Proposed（チームの合意待ち）
- 元になった議論：チーム内の議論メモ（このリポジトリには含めていない）

## ゴール（締切までに言えるようにすること）

1. **CAMP を OSS として公開した**：仕様書・実装・適合テスト・MIT ライセンス・ロゴつき README が、GitHub と npm で誰でも使える状態
2. **CAMP の技術効果を実測した**：コード削減・競合の解決・再接続・古いAI結果の破棄を、再現できるスクリプトで数字にした
3. **人間の意見が AI の案をどう変えたかを、会議ごとに見せられる**：因果の記録（Decision Provenance）と、会議の最後の「進化の流れ」画面
4. **小さな予備実験の結果を、正直な言い方で発表できる**：B（ふつうのAI支援）と C（IDEA AUDITION）の比較

時間が足りない場合は、上から順に優先する。1 と 3 はデモで必ず見せたいので削らない。4 は「やり方と予備結果」まででもよい。

方針（2026-11-08 夜、牧が決定）：
- 公開リポジトリ `camp-protocol/camp` と npm の組織 `@camp-protocol` は作成済み。公開リポジトリへの push は最初の1回（合言葉の廃止より前の版）だけにとどめ、**これ以上の push と npm への公開は、CAMP の更新と精度の改良をやり切ってから**まとめて行う（公開リポジトリの履歴を細かく汚さないため）
- 完成時にまとめてやること：
  1. 公開リポジトリの履歴を、英語のメッセージのコミットにまとめ直して force push する（今の日本語の5コミットと、Actions の実行記録を消す）。切り出しスクリプトも「英語の1コミットにまとめて出す」形に変える

  3. npm に公開し、アプリの3つの package.json を npm の版に切り替えてデプロイする
- それまでアプリは `workspace:*` で `packages/camp` を直接使う。最後に npm に出し、アプリの3つの package.json を npm の版に切り替える（コードの import は変えなくてよい）

## フェーズ2：Decision Provenance（因果の記録）（11/9）

「どの人間の判断が、どのAIの提案に影響したか」をプロトコルとアプリの両方で記録する。

### 2-1 CAMP 側（汎用）：イベントに「原因」を書けるようにする
- `event` メッセージに、任意のフィールド `causedBy?: string[]` を足す。中身は、そのイベントを引き起こしたコマンドの `commandId`、または前のイベントの `seq`
- `RoomApi.emit(type, detail, { causedBy })` と `task` の結果でそのまま渡せるようにする
- 任意のフィールドなので **CAMP v1 のまま後方互換**。仕様書に「Provenance」の節を足す
- 適合テスト：quick-vote で「VOTE → SUMMARY_READY（AIの要約）」の `causedBy` がたどれることを確かめる

### 2-2 IDEA AUDITION 側：版がどの発言を受けて作られたかを残す
- `Revision` に `provenance?: { utteranceSeqs: number[]; judgeIds: string[]; decisionAt?: number }` を足す
- `RefineTrigger` に、きっかけになった発言の `seq` を持たせる（`instruction` は発言そのもの、`promotion` は昇格の決定、迷いからの別案は迷いのシグナル）
- `CANDIDATE_REVISED` と改良完了のイベントに `causedBy` を付ける
- Firestore への追記にもそのまま残るので、あとから会議を再生して集計できる

### 2-3 対話サイクルの判定（純粋関数）
`domain/dialogue.ts` に、記録から次を数える関数を作る。

| 数えるもの | 判定のしかた |
|---|---|
| 対話の往復 | 人間の発言 → それを `provenance` に持つAIの版 → **その版に対する**人間の次の発言・決定（昇格・不合格・投票）、がそろったら1往復。さらにAIが応えれば2往復目 |
| 参加の均等さ | 審査員ごとの発言と決定の数から、正規化したエントロピー（0〜1、1が完全に均等） |
| 意見の反映 | 要望の発言ごとに「反映された／一部／されていない」を判定（2-4） |

### 2-4 意見が反映されたかの判定
イベントがつながっているだけでは反映されたとは言えないので、判定を別に行う。
- **本番（Gemini）**：要望文・変更前の版・変更後の版を渡し、`reflected | partial | not_reflected` と根拠を JSON で返させる。生成と同じプロンプトにはせず、評価専用の呼び出しにする
- **代わり（Gemini が使えない・テスト）**：要望の語が、変更後の版にあって変更前の版にないかを語彙の重なりで見る簡易判定
- 判定は会議の終わりにまとめて行う（会議中の負荷を増やさない）

### 2-5 指標に足す
`MetricsView` に `dialogue: { cycles, maxDepth, reflection: { reflected, partial, notReflected }, participation: number }` を足す。

## フェーズ4：CAMP の技術効果の実測（11/9、フェーズ2と並行）

| 指標 | 測り方 |
|---|---|
| コード削減 | kit に切り出す前（`8b206c2`）と後で、アプリ側の通信まわりの行数を比べる（`ws-server.ts` と、切り出す前の自作のクライアント → kit を使う `camp-client.ts`）。quick-vote の例が何行で書けるかも示す |
| 競合の解決 | N 人（4・8・16）が同じ枠に同時に操作するのを1000回。食い違いの数（0であるべき）、拒否された数、全員の最終状態が一致した割合 |
| 再接続 | ランダムに接続を切りながら操作を送り続け、送った操作が**ちょうど1回だけ**反映された割合（重複0・取りこぼし0であるべき） |
| 古いAI結果の破棄 | AIの処理中にリセット・取り消しを挟み、古い結果が状態に入らなかった割合 |
| 遅延 | コマンドを送ってから全員にイベントが届くまでの時間（中央値と p95、ローカル） |

## フェーズ5：予備実験（11/9 夜〜11/10）

締切までに3条件×3チームは難しいので、**B と C の比較だけ**を最小の規模で行う。

| 項目 | やり方 |
|---|---|
| 参加者 | VICTORY の4人＋協力してくれる人（他チーム・知人）。できれば2グループ以上 |
| 条件 | B：ふつうのチャットAI（Gemini アプリなど）を使いながら15分で1案に決める／C：IDEA AUDITION で15分 |
| 順序とテーマ | グループごとに B→C と C→B を入れ替える。テーマは難しさが近い2つを用意し、条件と入れ替える |
| 終了後のアンケート | 7段階：納得度・参加感・AIと協働した感じ。自由記述1問。アプリ内に小さな回答画面を作り、Firestore に保存（C 用）。B は同じ質問を Google フォームで |
| 案の評価 | 最初の案と最後の案を、出どころ（条件）を伏せて並べ、チーム外の人が「実現可能性・独自性・課題解決力」を10点で採点 |
| ログ | C は Firestore の記録から `dialogue` の指標を出す。B は会話を保存してもらい、往復を手で数える |

発表での言い方：
- 「n＝○グループの予備実験」「統計的に一般化できる結論ではない」と必ず書く
- 差が出なかった指標も載せる（「対話は増えたが、品質の差は確認できなかった」など）
- 「世界初」とは言わない。「アプリごとに個別に書いていた協調処理を、プロトコルとして標準化した」と言う

## 決めること（チームで）

1. 公開してよいか、ライセンスは MIT でよいか、著作者の表記
2. 予備実験に誰を呼ぶか（何グループ集められるか）
