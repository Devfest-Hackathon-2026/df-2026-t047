# 実験結果：人が同時に動き、遅い AI が割り込む会議を、従来の作りと CAMP で比べる

- 仕様：[2026-11-10-camp-vs-conventional.md](2026-11-10-camp-vs-conventional.md)
- 実行：`pnpm -C packages/camp bench`（シード 1、片道 40ms、Node v24.9.0、MacBook 1台、2026-11-10 早朝）
- 生データ：`packages/camp/bench/out/results.json`（修正前：`results-before-fix.json`）

## 発表用の1枚

会議中に各人の回線が2〜5秒ごとに一瞬切れる条件（S2、4人 × 20秒 × 5回、合計 2,200操作・質問 200件・切断 102回）と、AI が考えている間に話題を変える条件（S3、30回）。

| 作り | 消えた操作 | 二重になった操作 | 余分な AI の呼び出し | 前の話題の答えが混ざった | 全員の画面に出るまで（中央値） |
|---|---:|---:|---:|---:|---:|
| **IDEA AUDITION（CAMP）** | **0** | **0** | **0** | **0 / 30** | **84 ms** |
| WebSocket（Socket.IO の既定） | 18 | 0 | 0 | 30 / 30 | 83 ms |
| WebSocket＋送り直し（Socket.IO の retries） | 0 | 24 | 3 | 30 / 30 | 84 ms |
| HTTP の定期取得（1秒ごと） | 0 | 23 | 3 | 30 / 30 | 372 ms |

### 言い切れる一文

1. **「会議中に回線が一瞬切れる条件で、ふつうの WebSocket では操作が 18件消え、消えないように送り直すと 24件が二重になった。IDEA AUDITION はどちらも 0件」**（2,200操作・切断 102回）
2. **「AI が考えている間に話題を変えると、ふつうの作りでは 30回中 30回、前の話題の答えが新しい話題の画面に出た。IDEA AUDITION は 0回」**
3. **「それでも速さは変わらない。全員の画面に出るまで約 83〜84ms で、ふつうの WebSocket と同じ速さ。HTTP の定期取得（372ms）より4倍以上速い」**

### なぜ「このアプリでないと解けなかった」と言えるか

- 従来の作りは、**消える（最大1回）か、二重になる（最低1回）か**のどちらかしか選べない。Socket.IO の公式ドキュメントも、ちょうど1回は保証していない
- 会議では、二重は「同じ質問に AI が2回答える（お金が2倍）」「1回押した賛成が2回数えられる」になり、消えるのは「押したのに数えられていない」になる。どちらも会議の結論を変える
- AI の答えは数秒かかるので、その間に話題が変わる。届いた答えを「どの話題への答えか」で捨てない限り、前の話題の答えが混ざる（30回中30回）
- CAMP は、この3つに1つずつ守りを置いた：**操作ごとの ID で重複を捨てる**／**切れたら状態を取り直し、返事のない操作を同じ ID で送り直す**／**話題が変わる前に始めた AI の結果を捨てる**。守りのないところは1つもなく、余計なところもない。それぞれ数行の仕組みで、遅さにもならない（84ms 対 83ms）

| 8 | CAMP | 1,000 | 全員 1,000 | 1,191 ms |

| 8 | WS+再送 | 1,000 | 全員 1,000 | 217 ms |

| 16 | CAMP | 1,000 | 全員 1,000 | 613 ms |

| 16 | WS+再送 | 1,000 | 全員 1,000 | 322 ms |

- 4つとも正しい。**同時押しだけなら、サーバー1か所で処理すれば従来の作りでも解ける**（予想どおり）。差が出るのは、切断と遅い AI が入ったとき（S2・S3）
- CAMP が一度に送るときに遅いのは、クライアントが1人あたり1秒100件までに抑えて送るため（サーバーの送りすぎ防止に自分で当たらないように。下の「途中で見つけて直したこと」）。4人なら1人250件を一瞬で送る条件で、人の操作（1人で毎秒数回）では起きない

- HTTP は通信量が少ないが、1秒ごとの取得のぶん遅い（取得間隔を短くすれば速くなるが、そのぶん通信量が増える）

## 途中で見つけて直したこと（CAMP の不具合）

最初の実行で、**CAMP が S1 で失敗した**（4人：524件が消えた、8人：9,524件が二重）。原因は2つ。

1. **送りすぎ防止に自分で当たる**：サーバーは1本の接続で1秒120件を超えると切る。1人250件を一瞬で送ると切られ、つなぎ直したクライアントが返事待ちの250件を一度に送り直すので、また切られる、を繰り返した
2. **重複を捨てるための記録が、部屋全体で直近500件だけだった**：送り直しが重なると、ほかの人の操作に押し出された自分の操作がもう一度実行され、二重になった

直したこと（`exp/22-camp-bench` ブランチ。npm にはまだ出していない）：

- クライアントが Command を1秒100件までに抑えて送る（送り直しも同じ）。`packages/camp/src/client/camp-client.ts`
- 重複を捨てる記録を**送り手ごと**に500件にする（ほかの人の操作で押し出されない）。`packages/camp/src/core/idempotency.ts`
- テストを2つ足した（一度に250件送っても切られず全部に返事が来る：修正前は失敗することを確認／ほかの人の操作が多くても自分の結果は押し出されない）

修正前の数字は `results-before-fix.json` に残している。**人の操作の速さでは起きない条件だが、実験で見つけて直した**ことも、そのまま話してよい。

## 公平にするための約束（仕様書 3章）の確認

- [x] 4つとも、サーバーが1か所で状態を持ち、操作を1件ずつ処理する（`bench/impl/ws.ts`・`http.ts` は Node の1スレッドで同期的に反映。CAMP は部屋が1件ずつ）
- [x] 4つとも、切れたら同じ間隔（400ms から倍々、最大5秒）で再接続し、つながったら状態の全体を取り直す（`bench/impl/types.ts` の `backoff` は CAMP のクライアントと同じ式。WS は接続時に状態の全体を送り、HTTP は取得が状態の全体）
- [x] 4つとも、同じ会議の処理（`bench/meeting.ts`）・同じ偽の AI（同じシード）・同じ通信の遅れ・同じ切断の時刻
- [x] 4つとも、全員に状態の全体を配る
- [x] HTTP の取得間隔は1秒

## 限界

- 1台の PC の中で、中継を挟んで遅れと切断を作った。本物の回線は切れ方がもっと多様で、壊れる件数はもっと増えうる
- AI は偽物（1〜3秒で答える）。本物の Gemini は企画書で 10秒前後かかるので、話題が変わる前に答えが届かない場面はもっと多い
- 会議は模型（数える・質問する・次の提案へ）。本物の IDEA AUDITION は同じ CAMP の上に、案の作り置き・合意台帳などのアプリの守りがさらにある
- 比べなかったもの：Firestore のリアルタイム同期（仕様書 8章）
