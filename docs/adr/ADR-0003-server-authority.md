# ADR-0003: サーバー権威 — Cloud Run上のセッションアクター＋Firestoreへの追記

- Status: Accepted（2026-11-07。比較・検証の項目は Verification に残る）
- Owner: TBD
- Updated: 2026-11-07
- 関連：仕様書v5 第9.3・22.6・24・25.3章／open-questions Q1, Q4

## Context

- 最大4人が同時に操作する。同じキャラへの同時ドラッグ、残り1枠への同時昇格、満席時の要求、補充ジョブの二重実行を防ぐ必要がある。
- カーソル・ドラッグは高速、AI生成は低速。操作を生成待ちでブロックしない。
- Cloud Runは再起動・デプロイ・WebSocketのタイムアウトが起こり得る。**単一インスタンスのメモリを唯一の正本にしない**（25.3）。

## Decision（提案）

1. **セッションごとに1つのアクター（直列のコマンドキュー）**を、Cloud Runのサーバープロセス内に置く。
   - コマンドは1件ずつ処理する。Node.jsの単一スレッドとキューで、ロックなしに排他が成立する。
   - 処理の順序：検証（権限・状態・定員・`expectedVersion`）→ ドメインイベント生成 → `seq` を採番 → 全クライアントへ配信。
2. **確定イベントをFirestoreに追記する**（イベントログ）。一定間隔または重要イベントでスナップショットも保存する。
   - 配信は追記の完了を待たない（デモの体感を優先）。正本が失われるリスクは「スナップショット＋未保存の直近イベント」に限られる。※追記を待ってから配信する方式との比較は要検証。
3. **再起動時**：Firestoreの最新スナップショットとそれ以降のイベントを再生してアクターを復元する。
4. **MVPの構成**：`max-instances=1`、`min-instances=1`（コールドスタート回避）。スケールアウトは対象外とし、必要になったら共有状態（Redis等）やPub/Subを検討する。

### 主要な競合ケースの扱い

| ケース | 扱い |
|---|---|
| 同じキャラを2人が同時にドラッグ | 先に処理された `PROMOTION_REQUESTED` が勝つ。後者は `PROMOTION_REJECTED{reason: NOT_IN_LOWER}` を受けて元位置へ戻る |
| 残り1枠に3人が同時に昇格 | 1件だけ確定。残りは `UPPER_FULL` |
| 満席時の要求 | MVP：`PROMOTION_REJECTED{reason: UPPER_FULL}` を返し、クライアントはキャラを元の位置へ戻して「満席」を表示する（Q1回答済み） |
| 満席時の入れ替え（P1） | 上段の既存キャラに重ねてドロップすると `REQUEST_REPLACEMENT{incomingId, outgoingId}` を送る。アクターは1件の処理の中で「外れる側を `exiting`→`archived`（Idea BOXへ）」「入る側を `promoting`→`upper`」「下段に補充」をまとめて確定する。途中で失敗したら全体を取り消す |
| 補充の二重実行 | 補充はサーバーが `PROMOTION_CONFIRMED` の処理内でスロットを予約する。クライアントからの補充要求は受け付けない |
| 重複コマンド | `commandId` で重複を排除し、同じ結果を返す（ADR-0004） |
| Geminiのタイムアウト | 候補は先読みストックから補充する（ADR-0005）。ストックが空ならスロットを「準備中」表示にする |

### 投票と優勝決定（Q4回答済み、2026-11-07）

**決まったこと**：ソロはクリックで決定。複数人は1人1票の多数決で、同票ならホストが決める。

**ホスト**：セッションを作った審査員がホストになる。ホストが切断したら、接続中で最も早く参加した人にホスト役を移す（暫定）。

**細部の暫定案**（チームで確認する）：

| 項目 | 暫定案 |
|---|---|
| 投票を始められる人 | ホストだけ（「優勝を決める」ボタン）。上段に1体以上いることが条件 |
| 上段が1体だけのとき | 投票せず、ホストの確認だけで優勝にする |
| 投票中の上段と下段 | セッションを `champion_selection` に移し、昇格・入れ替え・改良の受付を止める。生成中の改良版は公開しない。下段の発表は止めて薄暗くする |
| 票の変更 | 締め切りまでは変更できる |
| 締め切り | 接続中の審査員が全員投票した時点、またはホストが締めた時点 |
| 切断した審査員 | 投票した票は有効。未投票なら母数から外す。再接続したら締め切り前なら投票できる |
| 同票 | ホストに同票の案だけを選択肢として示し、ホストが1つ選ぶ |
| 結果 | `CHAMPION_SELECTED` を全員に配信 → 優勝演出 → セッションを `completed` にする |

投票はアクターが状態として持ち、票の1つひとつを確定イベントとしてFirestoreに追記する。再接続した人にはスナップショットで投票状態を返す（AC-37）。

## Alternatives

| 案 | 利点 | 欠点 |
|---|---|---|
| Firestoreトランザクションを正本にする | 永続性が高く、サーバーの再起動に強い | 書き込みのたびに遅延が乗り、同一ドキュメントへの競合で再試行が増える。ドラッグの手触りに影響 |
| Firebaseのリアルタイム同期のみ（サーバーなし） | 実装が少ない | 定員・一意性の排他をクライアント主導で保証しにくい。AI処理を担う場所が別途必要 |
| **メモリのアクター＋Firestore追記（本提案）** | 低遅延・単純な排他 | インスタンス移行時に整合が崩れるリスク。単一インスタンスの前提 |

## Consequences

- ドメインロジックはアクター内に集約され、テストしやすい。
- Cloud Runのインスタンス入れ替え中に2つのインスタンスが並存する可能性があり、実機検証が必要（要検証）。
- 書き込みを待たずに配信する方式では、直近数件のイベントを失う可能性を受け入れる必要がある。

## Verification

1. 2台で同じキャラを同時にドラッグ → 二重昇格しない。
2. 上段残り1枠に3台から同時に昇格 → 1件だけ確定。
3. サーバーを強制再起動 → クライアントが再接続し、スナップショットから同じ状態に戻る。
4. 4台を接続した状態でデプロイ → 切断から復帰までの時間を測る。

## 実装メモ：Firestore への保存と復元（2026-11-07）

- データベース：`(default)`、Native モード、`asia-northeast1`。
- 構成：
  - `sessions/{sessionId}`：`seq`、`status`、`theme`、`state`（ドメインの状態を JSON 文字列で保存。Firestore が入れ子の配列を扱えないため）、`updatedAt`
  - `sessions/{sessionId}/events/{seq}`：確定イベント（`type`、`detail`、`actorJudgeId`、`correlationId`、`at`）。追記のみ
- 書き込み：配信は保存を待たない。約300msごとに、たまったイベントと最新状態を1つのバッチで書く。失敗したら5秒後に再試行し、イベントは失わない。終了時（SIGTERM）に未保存分を書き出す。
- 復元：セッションへの最初の接続時に読み込む。全員を「切断中」、途中だった改良を「準備完了」に戻し、下段の自動入れ替えと先読みを再開する。審査員は同じ judgeId で再接続すれば同じ審査員に戻り、ホストも再設定される。
- 確認：ローカルでサーバーを再起動し、同じ URL を開くと上段・下段・版・審査員が元どおりに戻ることを確認した（`session restored: persist1 seq=12`）。
- ローカル開発の認証は Gemini と同じく `LOCAL_GCLOUD_CONFIG`（ADC を上書きしない）。
