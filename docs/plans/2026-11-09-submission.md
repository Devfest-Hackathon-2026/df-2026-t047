### 審査基準（8項目 × 0〜3点 ＝ 24点）

| 観点 | 項目 | IDEA AUDITION で見せるもの |
|---|---|---|
| 1. Google 技術の活用 | a. Google 技術がプロダクトの中核で有効に機能しているか | Gemini が案の生成・改良・相互批評・回答・合意台帳・企画書・音声の文字起こし・埋め込み（好みの判定）を担う。Cloud Run・Firestore |
| | b. 採用した理由が合理的かつ具体的に説明されているか | ADR の比較（なぜ Vertex AI か、なぜ Cloud Run 1台か、なぜ Firestore か） |
| 2. プロダクトの完成度 | a. 課題解決に必要な操作が一連の流れとして動くか | 部屋を作る → 招待 → 審査 → 決勝 → 優勝 → 企画書、が本番で通る |
| | b. 対象ユーザーが目的を達成できる UI・UX か | #1〜#13 のうち UI まわり |
| | c. 安全性・拡張性・保守性を見据えた設計か | サーバー権威（ADR-0003）、CAMP（同時操作で壊れない、OSS）、秘密情報をリポジトリに置かない、テスト（約150件） |
| 3. 社会課題への解決力 | a. 解決する課題が具体的かつ明確か | 会議でアイデアが出ない・声の大きい人に決まる。根拠つきで（M2 #19） |
| | b. 機能や仕組みが課題解決に有効か | 実測・アンケート（M1 #18・M3 #20） |
| 4. ピッチの構成と説明力 | a. デモ・話の構成が分かりやすくインパクトがあるか | スライド（#16）・デモ（#17） |

- 採点外（必須記入）：AI をどの場面でどう使ったか・なぜか、開発を通して何を得てどれだけ成長したか
- 審査対象外：デモ動画の偽装、他社 AI ツールが前面に出ている、テーマ・カテゴリ外、必須項目の不足、Google Cloud の実行基盤を使っていない、など

### テーマ・カテゴリ・ルール

- テーマ：**“Own the Why, Build with Intent.”**（AI の提案を鵜呑みにせず、人間が主導権を握って比べ、「なぜそれを選んだか」を自分の言葉で語る）。IDEA AUDITION は「AI が複数案を出し、人間が理由を持って選ぶ」アプリなので、テーマとそのまま重なる
- カテゴリ（カテゴリ外は審査対象外）：医療・福祉／観光／教育／エンターテインメント／クリエイティブ。**候補はクリエイティブ**（企画・アイデアづくり）。エンターテインメントも考えられる
- AI・他社ツール：開発での AI コーディング支援は可。プロダクトのメインの技術は Google 技術。**デモ・ピッチで他社製品を前面に出さない**。IDEA AUDITION の AI は Gemini だけ（`@google/genai`）なので問題ない
- 開発開始前（11/5 10:00 前）にコードを書くのは禁止：最初のコミットは 2026-11-07 なので問題ない
- API キーや秘密情報をリポジトリにコミットしない（審査項目「安全性」にも関わる）
- 著作物利用シート：使った素材・ライブラリ・データの出典とライセンス
- 連絡は Discord（announce-all）、質問は「お問い合わせ」チャンネル

## Own the Why（運営が求めている AI との付き合い方）

- AI の提案を鵜呑みにせず、複数案を出させて pros/cons を比べて選ぶ
- 選んだ理由と捨てた案をメモしておき、ドキュメントの「選定理由・メリット/デメリット」に書く
- 「誰の・どんな課題か」を根拠つきで書く

**今あるもの**：ADR（docs/adr、0001〜0011）に、案の比較・選んだ理由・捨てた案が残っている（描画方式、サーバー権威、AI の組み立て、合意台帳、好みエンジン、CAMP など）。これを必須 3 の「選定理由・メリット/デメリット」と、採点外 8 の材料に使える。アプリ自体も「AI に複数案を出させ、人間が理由を持って選ぶ」作りなので、Own the Why と主張がそのまま重なる（発表の強みにも使える）。

## 気をつけること

- **11/14 までの費用**：審査員が「AI：Gemini」で遊ぶとクレジットを使う。予算アラートはあるが自動では止まらない
- **締切後の変更**：提出後は本番を壊さない。直すなら、動作を確かめてからデプロイする
