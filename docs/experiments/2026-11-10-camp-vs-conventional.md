# 実験仕様：人が同時に動き、遅い AI が割り込む会議を、従来の作りと CAMP で比べる

- 対応 issue：[#22](https://github.com/yuto-valiark/idea-audition/issues/22)（CAMP の技術効果を実測する）
- 関係：[実測計画](../plans/2026-11-10-measurement-plan.html) の M1・M2。この実験は、その土台になる「通信の作り方」の比較
- ブランチ：`exp/22-camp-bench`（main は汚さない）
- コード：`packages/camp/bench/`（npm には入らない。`package.json` の `files` の外）
- 結果：[2026-11-10-camp-vs-conventional-results.md](2026-11-10-camp-vs-conventional-results.md)

## 1. 何を示したいか

**主張**：数人が同時に操作し、そこへ数秒かかる AI の結果が割り込む会議では、ふつうのリアルタイム通信の作りでは「操作が消える」「二重になる」「古い AI の結果が新しい話題に混ざる」が起きる。IDEA AUDITION は、そのために作った CAMP でこれを0にしている。

発表で思わせたいことは2つ。

1. **このアプリでないと解けなかった**：従来の作り（Socket.IO と同じ作り・HTTP の定期取得）を、同じ条件・同じ処理で動かすと、実際に壊れる。数字で見せる
2. **まっすぐな解き方だった**：壊れ方は3つだけで、それぞれに1つずつ守りがある（順番・重複の排除・古い結果を捨てる）。従来の作りに守りを足していくと、結局 CAMP と同じものになる

「正しく作ったので0件でした」だけでは弱い。**同じ入力を従来の作りに流すと何件壊れるか**を並べて、差を見せる。

## 2. 先に調べたこと（実験の前提）

| 調べたこと | わかったこと | どこで確かめたか |
|---|---|---|
| CAMP が保証していること | ① 部屋ごとに1件ずつ処理し、連番 `seq` を振って全員に同じ順で配る ② 操作には必ず成否が返る ③ `commandId` で重複を捨て、同じ結果を返す（直近500件）④ 切れたら自動で再接続し、状態の全体を取り直し、返事のない操作を同じ `commandId` で送り直す ⑤ `room.task()` の結果は、`room.reset()` をまたいだら捨てる | `packages/camp/src/server/room.ts`、`src/client/camp-client.ts`、`SPEC.md` |
| ふつうの作り（Socket.IO）の保証 | 既定は**最大1回**（切れた瞬間に送ったものは届かないことがあり、送り直さない）。切れている間はクライアントがためて、つながったら送る。`retries` を設定すると**最低1回**（返事が来るまで送り直す）。二重に届いたものを捨てる仕組みはなく、アプリに任される | [Socket.IO：Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees) |
| 実際の AI の遅さ | 本物の Gemini で、企画書の文章 11.9秒・画像 5.0秒（2026-11-09 ローカル実測）。質問への答えは数秒 | 実測（#44 の確認時） |
| アプリでの使い方 | 本番の `SessionActor` は CAMP の `createCampTransport` に乗っている。今回の実験は、同じ部品（`@camp-protocol/kit`）で作った会議の模型で測る | `apps/server/src/application/session-actor.ts` |

## 3. 比べる4つの作り

全部、**同じ会議の処理**（`bench/meeting.ts`：数える・質問する・AI が答える・次の提案へ）を使う。違うのは、通信と、そこにある守りだけ。

| 記号 | 作り | 中身 | 現実の例 |
|---|---|---|---|
| **CAMP** | IDEA AUDITION の作り | `@camp-protocol/kit` の `createCampServer` と `CampClient` をそのまま使う | このアプリ |
| **WS** | WebSocket（最大1回） | サーバーが状態を持ち、操作が来たら処理して全員に配る。切れたら同じ間隔で再接続し、つながったら状態の全体を受け取る。切れている間の操作はためて、つながったら送る。返事は待たない | Socket.IO の既定 |
| **WS+再送** | WebSocket（最低1回） | WS に「返事（ack）が来るまで送り直す」を足したもの。サーバーは重複を捨てない | Socket.IO の `retries` |
| **HTTP** | HTTP の定期取得 | 1秒ごとに状態を取りに行く。操作は POST。失敗したら送り直す | REST＋ポーリング |

### 公平にするための約束（比べる相手をわざと弱くしない）

- [x] 4つとも、サーバーが1か所で状態を持ち、操作を1件ずつ処理する（同時押しで数がずれる素朴な作りにはしない）
- [x] 4つとも、切れたら同じ間隔（400ms から倍々、最大5秒）で再接続し、つながったら状態の全体を取り直す
- [x] 4つとも、同じ会議の処理・同じ偽の AI・同じ通信の遅れ・同じ切断の時刻（乱数のシードでそろえる）
- [x] 4つとも、全員に状態の全体を配る（送るデータの形をそろえ、通信量の差が作りの差だけになるように）
- [x] HTTP の取得間隔は、よく使われる1秒にする（短くした場合の通信量も書く）

## 4. 共通の条件

| 項目 | 値 | 理由 |
|---|---|---|
| 通信の遅れ | 片道 40ms（往復 80ms）。S4 だけ 0ms でも測る | 4G・混んだ Wi-Fi くらい |
| 通信路 | クライアントごとに中継（TCP プロキシ）を挟む。遅れを足し、指定の時刻に接続を切る。**切ると、その時点で中継の途中にあるデータは消える** | 実際の切断と同じ。「送ったつもりで届いていない」が起きる |
| 偽の AI | 質問1件ごとに 1〜3秒（乱数）で答えを返す。呼ばれた回数を数える（＝お金） | 本物の Gemini の数秒に合わせる |
| 乱数 | シードで固定。同じシードなら同じ操作・同じ切断 | 何度でも同じ結果を出せる |
| 動かす場所 | 1台の PC（ローカル）。サーバー・中継・クライアントを1つのプロセスで動かす | 外のネットワークの揺れを入れないため |

## 5. 4つの場面と、測るもの

### S1 同時操作：みんなが同時に押しても、全員の画面が同じか（#22 の1つ目）

- 4・8・16人が、合わせて1,000回「反応（数を1つ増やす）」を、できるだけ同時に送る。切断なし
- 測る：サーバーの数（正解は1,000）、全員の画面の数が一致したか、全部そろうまでの時間、通信量
- 予想：4つとも正しい（サーバーが1か所で処理するので）。**同時押しだけなら従来の作りでも解ける**ことを正直に示す。差は時間と通信量に出る

### S2 切断しながら操作：ちょうど1回だけ反映されるか（#22 の2つ目）

- 4人がそれぞれ、20秒の間に「反応」100回と「質問」10回を、ばらばらの間隔で送る
- その間、各人の接続を 2〜5秒ごとに切る（会議中に Wi-Fi が一瞬切れる・電車でつながりにくい、の再現）
- シード5つで5回まわす
- 測る：
  - **消えた操作**（送ったのに反映されなかった）
  - **二重になった操作**（1回押したのに2回反映された）
  - **余分な AI の呼び出し**（同じ質問に2回答えさせた回数。そのぶんお金がかかる）
  - 最後に全員の画面がサーバーと一致したか
- 予想：WS は消える。WS+再送は二重になる（同じ質問に AI が2回答える）。HTTP は送り直しで二重になる。CAMP は0

### S3 AI の処理中に話題が変わる：古い結果が入らないか（#22 の3つ目）

- 質問を送り、AI が答えを考えている間（0.3〜0.9秒後）に、ホストが「次の提案へ」を押す。30回
- 測る：**前の提案への答えが、次の提案の画面に出てしまった回数**
- 予想：CAMP は0（`room.task` が `reset` をまたいだ結果を捨てる）。ほかの3つは、守りを書かない限り混ざる

### S4 反映までの時間：押してから全員の画面に出るまで（#22 の4つ目）

- 4人で200回、1秒に10回くらいの間隔で「反応」を送る。切断なし。片道 0ms と 40ms の2通り
- 測る：送ってから**全員の画面**に反映されるまでの時間の中央値・95%点・最大、1回の操作あたりの通信量（バイト・メッセージ数・HTTP の回数）
- 予想：WS・CAMP はほぼ同じ（CAMP の守りは遅さにならない）。HTTP は取得間隔のぶん遅い（中央値で0.5秒前後）

## 6. 判定の基準

| 場面 | CAMP が満たすべきこと | 満たさなかったら |
|---|---|---|
| S1 | 全員の数が1,000で一致 | CAMP の不具合として issue にし、結果にもそのまま書く |
| S2 | 消えた操作0・二重0・余分な AI の呼び出し0・最後に全員一致（5回とも） | 同上 |
| S3 | 古い答えが出た回数0 | 同上 |
| S4 | 中央値が WS の 1.5倍以内 | 遅さとして正直に書き、原因を見る |

比べる相手に差が出なかった項目も、消さずに載せる。

## 7. 完了の条件

1. `pnpm -C packages/camp bench` の1回で、4つの作り × 4つの場面がまわり、結果が出る。シードを同じにすれば同じ結果になる
2. 結果を JSON（`bench/out/results.json`）と表（[結果のページ](2026-11-10-camp-vs-conventional-results.md)）に出す
3. 6章の基準で判定し、結果のページに「満たした／満たさなかった」を書く
4. 3章の「公平にするための約束」を、コードで1つずつ確かめてチェックを入れる
5. 発表用に、1枚の表と、言い切れる一文を3つ書く
6. 結果の限界（ローカル・模擬の通信・偽の AI・会議の模型）を書く
7. 既存のテスト（CAMP 19件ほか）が通る。npm に出すものは変えない

## 8. やらないこと

- **Firestore のリアルタイム同期との比較**：エミュレーターの用意と、書き方の選び方（トランザクションを使うか）で結論が変わり、今日の時間では公平に作れない。「今後」に書く
- **本物の Gemini を使う**：お金と時間がかかり、遅さもばらつく。遅さは偽の AI で再現する
- **本番のサーバーで測る**：作り直しの比較なので、ローカルで同じ条件にそろえる方が正しい
- **人の満足度・案の質**：実測計画の M6（ユーザー実験）の担当

## 9. 予想される反論と、答え

| 反論 | 答え |
|---|---|
| 「Socket.IO でも、重複を捨てる処理を書けばいい」 | その通り。順番・重複の排除・切れたら取り直す・古い AI の結果を捨てる、を全部書くと CAMP になる。CAMP はそれを1回作って、npm で誰でも使えるようにしたもの |
| 「比べる相手をわざと弱く作ったのでは」 | 3章の約束どおり、4つともサーバーが1か所で処理し、再接続して状態を取り直す。違いは Socket.IO の公式ドキュメントに書かれている保証の範囲だけ |
| 「ローカルの模擬だから現実と違う」 | 切断と遅れは中継で再現し、シードで再現できるようにした。壊れる件数は現実の回線ではもっと増えうる（切れ方がもっと多様） |

## 10. 発表での見せ方（案）

- 1枚の表：行＝4つの作り、列＝消えた操作／二重／余分な AI の呼び出し／古い答えが混ざった／反映までの時間（中央値）
- 言い切る一文（数字は結果で埋める）：
  1. 「会議中に回線が一瞬切れる条件で、ふつうの WebSocket では操作が N件消え、送り直すと M件二重になった。IDEA AUDITION は0件」
  2. 「AI が考えている間に話題を変えると、ふつうの作りでは前の話題の答えが K回混ざった。IDEA AUDITION は0回」
  3. 「守りを入れても、反映までの時間は WebSocket と同じ X ms。HTTP の定期取得より Y 倍速い」
